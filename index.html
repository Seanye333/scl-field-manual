        Chapter 01

        Why SCL

        SCL (Structured Control Language) is Siemens' implementation of Structured Text from the IEC 61131-3 standard — a Pascal-like, high-level text language that compiles to the same machine code as ladder logic. Everything you can do in LAD/FBD you can do in SCL, and a large class of problems is dramatically easier in text:

        • Math and formulas — scaling, PID pre-processing, totalizers, geometry. One line of SCL replaces a page of MOVE/CALCULATE boxes.
        • Loops over arrays — checking 32 zones, averaging 100 samples, searching a recipe table. LAD simply has no good answer to FOR.
        • State machines — a CASE statement reads like the sequence spec itself.
        • String and recipe handling — barcodes, telegram parsing, filenames.
        • Version control & review — text diffs cleanly; you can read a change in a pull request.

        Where LAD still wins: simple interlock chains that electricians and maintenance staff will troubleshoot live with power-flow highlighting. Real projects mix both — a common professional pattern is LAD for the safety/interlock layer, SCL for logic, sequencing and data handling. Mastering SCL doesn't mean abandoning ladder; it means never being limited by it.

        How this manual worksEach chapter is short theory plus compilable code (every code panel has a copy button). Type the examples into a real project — TIA Portal + PLCSIM costs nothing extra if you have Portal, and the trial download runs 21 days. When you finish a chapter, hit Mark chapter complete at its end; the sidebar keeps your score. Reading SCL teaches you syntax; typing it and watching the compiler complain teaches you the language.
        Check yourself

        Which task is SCL clearly better at than ladder logic?

        Loops over arrays are SCL's home turf — ladder has no good FOR. The simple interlock is the case where LAD's power-flow view still earns its keep.

        SCL is Siemens' implementation of which IEC 61131-3 language?

        Structured Text (ST). That's why most SCL skills transfer to CODESYS, Rockwell ST, Beckhoff and others with only dialect changes.

        Multi-instance: FBs inside FBs

        Declaring an FB (or a timer — timers are FBs too) in the Static section of another FB embeds its instance data inside the parent's DB. One motor FB with three internal timers = one DB, not four. This is how professional libraries stay tidy:

        Rule of thumbStateless math → FC. Anything with a timer, edge, counter, or remembered mode → FB. If you find yourself passing "memory" bits into an FC so it can fake state, it should have been an FB.
        Check yourself

        A block computes flow-corrected volume from three inputs — no timers, no history. FB or FC?

        No state → FC. It needs no instance DB and its output depends only on this call's inputs, which also makes it trivially testable.

        Declaring tDelay : TON; in an FB's Static section (multi-instance) means…

        One device FB, one DB — the parent's instance DB contains all embedded instances. This is what keeps a 40-motor project at 40 DBs instead of 200.

        What does the expression 7 / 2 evaluate to?

        Both operands are integers, so the division is integer division — the result truncates to 3. Convert first (7.0 / 2.0) for 3.5.

        A 32-bit Real has ~7 significant digits — once the total is large, small increments vanish into rounding. LReal's ~15 digits keep the additions meaningful.

        Variables & interfaces

        Every block's interface has fixed sections. Where you declare a variable decides its lifetime and who can see it:

        SectionDirectionPersists between cycles?Notes
        InputCaller → blockFB: yes (in instance DB)Read-only inside the block (by convention)
        OutputBlock → callerFB: yesWrite from inside, read by caller with =>
        InOutBoth waysReference to caller's dataRequired for passing STRING, ARRAY, STRUCT/UDT to FCs — passed by reference, no copy
        StaticinternalYes — this is FB memoryTimers, edge memory, step numbers, multi-instances. FBs only
        TempinternalNo — garbage each callScratch variables. Write before you read, every single call
        Constant—compile-timeNamed numbers: MAX_ZONES : Int := 16
        The Temp trapTemp variables are not initialized. Reading one before writing it in the same call gives you whatever was left on the stack — logic that works in simulation and fails randomly on hardware. If a value must survive to the next cycle, it belongs in Static.

        Optimized block access

        New blocks default to optimized access: the compiler arranges variables for speed, and you address everything symbolically — there are no fixed byte offsets, no DB10.DBW4. Keep it on. You only switch a DB to standard (non-optimized) access when an external system needs absolute addresses — some HMI/SCADA drivers, open TCP telegrams via TRCV, or legacy migration. Even in optimized blocks you can still reach individual bits of a word with slice access:

        Default values and retentivity

        Mark Static data RETAIN when it must survive a power cycle (totalizers, service counters, selected recipe). Everything else should re-initialize cleanly — a machine that "remembers" it was mid-sequence through a power cut is a hazard unless you designed for it.

        Check yourself

        A value must survive from one scan to the next inside an FB. It belongs in…

        Temp is garbage at the start of every call. Static is the FB's memory — that's the whole difference between an FB and an FC.

        You must pass a 200-element UDT array into an FC. Which section avoids copying it?

        Structured data through InOut travels as a reference, no copy. For FCs it's required for STRING/ARRAY/STRUCT anyway — and it's why Ch. 9's motor FB takes its UDT that way.

        Code reads a Temp variable before writing it this scan. In PLCSIM it works. On the CPU…

        Temp is not initialized. Simulation often hides it by happening to hand you zeros. Hardware won't be so polite.

        Chapter 07

        Control flow

        IF / ELSIF / ELSE

        CASE — the workhorse

        CASE selects on an integer expression. Always write the ELSE branch — an unexpected value should do something deliberate, not silently nothing.

        Loops

        Loops run inside one scanA PLC loop does not wait — the entire FOR completes within the current cycle. A WHILE whose condition never becomes false doesn't "run forever in the background"; it stalls the scan until the cycle-time watchdog stops the CPU. Never make a loop wait for an input to change — that's what state machines (Ch. 11) are for.
        Check yourself

        A WHILE loop waits for a proximity sensor to turn TRUE. The sensor is currently FALSE. What happens?

        Inputs are read once per scan — inside the loop the sensor value never changes, so the loop can never end. Cross-cycle waiting is a state machine's job.

        CASE #x OF has branches for 1, 2, 3 and no ELSE. #x is 99. What runs?

        Legal, silent, and usually a bug: whatever the branches were supposed to maintain simply doesn't happen. Always write the ELSE.

        FOR #i := 1 TO 10 DO — how many iterations?

        Both bounds are inclusive: 1 through 10.
        Chapter 08

        Timers, counters & edges

        IEC timers and counters are system FBs — you declare an instance (Static or multi-instance) and call it like any FB. The call must execute every cycle for the timer to update.

        TONOn-delay: Q true after IN held true for PTDebounce, feedback supervision, "still running after 5 s?"
        TOFOff-delay: Q holds true for PT after IN dropsFan run-on, valve hold-open
        TPPulse: Q true for exactly PT once triggeredFixed-length lubrication shot, horn pulse
        TONRAccumulating on-delay with reset inputRuntime totalizer
        CTU / CTD / CTUDCount up / down / both, with preset PV and output QPiece counting, batching
        R_TRIG / F_TRIGOne-cycle pulse on rising / falling edge of CLKButtons, one-shot actions, counting events

        Chapter 10

        Strings & conversions

        Strings carry batch IDs, barcodes, error texts, and telegram fragments. A String[20] reserves 20 characters plus 2 length bytes. Always size strings — the default String is 254 chars and bloats DBs and InOut transfers.

        Strings and performanceString operations copy data and are far more expensive than integer math. Fine in an event-driven branch (a scan of a barcode); avoid rebuilding strings unconditionally every cycle in fast cyclic OBs.

        Why declare String[20] instead of plain String?

        A default String costs 256 bytes every time it appears. Twenty batch-ID strings of the right size cost less than two default ones.

        String operations copy bytes around. Gate them behind an edge (new barcode, changed state) and the cost disappears.
        Chapter 11

        State machines

        This is the chapter that turns you from "writes SCL" into "programs machines." Almost every real process is a sequence — fill, heat, hold, drain — and the professional pattern is a CASE-based step machine in an FB: one Static step number, one CASE, explicit transitions.

        The discipline that makes this pattern scale:

        • Transitions only set the step number. Outputs are computed from the state after the CASE, in one block — no output is ever set in two places.
        • Number steps in tens (10, 20, 30…) so you can insert step 15 later without renumbering.
        • Name steps with constants. #step := #DRAIN reviews itself; #step := 40 doesn't.
        • Expose stepNo to the HMI. "It's stuck in step 20" is a diagnosis; "it's stuck" is a phone call at 2 a.m.
        • Every waiting step needs an exit — a transition, a timeout to a fault step, or both. A step that can wait forever will.
        The shared-step-timer trapLook again at the #stepOld line. Without it there is a genuine bug: an IEC timer's ET only resets when IN goes FALSE. If two consecutive steps are both timed (MIX → DRAIN here), IN stays TRUE straight through the transition — the timer never resets, ET is already past the new (shorter) PT, and Q fires immediately: the second step's time is silently skipped. Comparing #step to last scan's value drops IN for exactly one cycle on every step change, restarting the timer. Try it in the Playground: the star-delta example is wired this way — remove the stepOld term and watch the 100 ms gap step vanish.
        Check yourself

        In a step machine, where should the valveFill output be written?

        If FILL sets it TRUE, some other branch must remember to set it FALSE — and one day nobody does. #valveFill := #step = #FILL; can never be stale.

        Why number steps 10, 20, 30 instead of 1, 2, 3?

        Pure engineering pragmatism, inherited from line-numbered BASIC and STEP 5 — and still the convention your colleagues expect.

        A waiting step whose transition condition never comes true will…

        Unlike a stuck loop, a stuck step is scan-friendly and invisible until production stops. Every waiting step needs a designed exit — often a timeout into a fault step.
        Chapter 12

        Reusable FB design

        The payoff of everything so far: device FBs you write once, test once, and drop into every project. Here is a production-shaped motor block combining UDTs, timers, edges, and fault latching:

        Design rules for library blocks

        • No global tags inside the FB. Everything through the interface. The block must not know it's in "Line 3" — that's what makes it reusable and simulatable.
        • Inputs are commands and measurements; outputs are actions and status. The caller wires them to reality.
        • Fail safe by structure: the output line cmdRun AND interlockOK AND NOT fault means any fault path automatically drops the contactor — you can't forget to turn it off in some branch.
        • Fault codes, not just fault bits. An Int costs nothing and tells maintenance exactly what happened.
        • Version your blocks (block properties → version) and never edit a released library block in a project — copy, bump, retest.

        Going generic

        For true one-block-fits-all libraries, S7-1500 adds Variant parameters and REF_TO references — Chapter 16 covers them. Learn them after UDT + Array[*] patterns feel routine: 90% of practical genericity comes from those two.

        Check yourself

        Why must a library FB never read a global tag directly?

        Everything through the interface. A block that references "Line3_Fault" internally cannot go into a library, a different project, or a PLCSIM test bench.

        In FB_MotorCtrl, why is #contactor := #cmdRun AND #interlockOK AND NOT #fault; safer than switching the output off inside each fault branch?

        Fail-safe by structure: safety comes from the shape of the logic, not from remembering to write the off-command in each of five places.
        Chapter 13

        Closed-loop control

        Temperature, pressure, flow, level — sooner or later you'll close a loop. Two things matter: understanding the math well enough to not fear it, and knowing the Siemens way of running it.

        Rule one: control runs in a cyclic interrupt

        OB1's cycle time varies with program load — poison for a controller, whose math assumes a fixed sample time. Create a cyclic interrupt OB (OB30, e.g. every 100 ms) and call all closed-loop control there. The OS interrupts OB1 to run it exactly on schedule.

        PID_Compact is a technology object: an FB plus a configuration and commissioning UI. Add it under Technology objects, then call it from your cyclic interrupt:

The commissioning trend view is also a decent free loop analyzer — watch the response to a setpoint step before you trust any tuning.

        Know the math anyway: a PI controller in 6 lines

        Writing one yourself, once, demystifies every tuning conversation you'll ever have:

        Read the anti-windup line twice: without clamping the integrator, a loop that sits saturated (heater at 100 %, still too cold) accumulates a huge iTerm and then massively overshoots. This single line is the difference between a controller and a lesson.

        Sample time disciplineTs_s must equal the real OB cycle time. Move the call from a 100 ms OB to OB1 and the integral action becomes wrong by an unknown, varying factor. This is the most common "the PID behaves differently on the real machine" cause.
        • Filter noisy inputs before the controller, not after: #pvFilt := #pvFilt + 0.2 * (#pvRaw - #pvFilt); is a one-line low-pass.
        • Bumpless start: when switching to automatic, preset iTerm so the output doesn't jump (PID_Compact handles this for you).
        • Use Trace (Ch. 18) on setpoint, PV and output together — tuning by watch table alone is guesswork.
        Check yourself

        The heater sits at 100 % for ten minutes while the tank warms up. Without anti-windup, when the temperature finally reaches setpoint the loop will…

        That's integrator windup. Clamping iTerm to the output range is the one-line cure — find it in FB_PI.

        Ts_s in FB_PI must equal…

        The integral multiplies the error by the sample time. If the code says 100 ms but the OB runs at 250 ms, integral action is 2.5× too weak — and worse, OB1's varying cycle makes it drift.
        Chapter 14

        Talking to the world

        A PLC that only talks to its own I/O is rare. The communication landscape, from easiest to most manual:

        ChannelMechanismYou write
        HMI / SCADA (Siemens)Symbolic tag access over PROFINETNothing — just structure your DBs well
        PLC ↔ PLC (Siemens)GET/PUT S7 communicationOne call per transfer; enable "Permit access via PUT/GET" on the server CPU
        Modbus TCP devicesMB_CLIENT / MB_SERVERRegister maps and polling logic
        Anything TCP/UDPOpen User Communication: TSEND_C / TRCV_CThe whole telegram format — full control, full responsibility

        Design the HMI interface DB deliberately

        The HMI should read curated data, not your internals. One global DB (e.g. DB_HMI) with commands in, status out — the same interface thinking as an FB, at project scale. It also means you can refactor logic without breaking a hundred HMI tag references.

        Open User Communication in SCL

        Structured data → bytes: Serialize

        Rather than hand-packing bytes, Serialize / Deserialize convert a UDT to/from a byte array in the S7 format (big-endian):

        Byte order is realS7 CPUs are big-endian; most PC software and many devices expect little-endian. If values arrive scrambled (e.g. 256 instead of 1), you're looking at swapped bytes — use SWAP or define the telegram byte-exactly and document it. Half of all commissioning-week comms bugs are this paragraph.
        • Status/error outputs of comm blocks are not optional reading — latch STATUS on ERROR so you can look it up after the fact.
        • Comm blocks work asynchronously across many cycles: trigger with an edge, then wait for DONE/ERROR — a small state machine (Ch. 11) around each transfer is the professional pattern.
        • For telegram buffers accessed by external partners byte-by-byte, a non-optimized DB keeps the layout predictable.
        Check yourself

        A PC application reads your counter as 512 when the PLC shows 2. The cause is almost certainly…

        2 = 16#0002; swap the bytes and you get 16#0200 = 512. Define the telegram byte-exactly and swap where needed.

        TSEND_C returned ERROR for one scan. What must your code have done for you to diagnose it later?

        Comm block outputs are valid for one cycle. If STATUS isn't captured on the error edge, the diagnostic code is gone before anyone can look it up.
        Chapter 15

        Interrupts, startup & OBs in depth

        Chapter 3 introduced OBs as "entry points the OS calls." Here is the fuller map — knowing which OB to put code in is half of program design:

        OBFires when…Put here
        OB1Continuously, as fast as the program allowsThe main machine logic — sequences, device FBs
        OB30–38 cyclic interruptOn a fixed clock (e.g. every 100 ms), preempting OB1Closed-loop control, filtering, anything needing a fixed sample time
        OB40–47 hardware interruptA configured input edge or module eventTime-critical reactions (registration marks, fast reject gates)
        OB100 startupOnce, on STOP → RUNInitialization: presets, handshakes, forcing a known state
        OB82 / 83 / 86 diagnosticsModule fault / removal / rack failureFlag the fault for the HMI; their mere presence keeps the CPU in RUN
        OB121 / 122 errorProgramming error / I/O access errorLog and contain — again, presence changes behavior (S7-1500 also offers settable reactions)
        OB10x / OB2xTime-of-day / time-delayScheduled actions (daily totals reset), delayed one-shots

        Startup: put the machine into a known state

        Design rule: after any power cycle the machine either resumes deliberately (you wrote resume logic) or resets deliberately (OB100 forces it). Whatever the retained step number says, an operator must confirm before motion. "It just continued where the RAM happened to be" is how machines hurt people.

        Preemption and data consistency

        A cyclic interrupt preempts OB1 mid-statement-sequence. If OB1 is halfway through updating a multi-field setpoint struct when OB30 reads it, OB30 sees a half-written mix — a bug that appears once a week and never in simulation. Rules that keep you safe:

        • Keep interrupt OBs short — call the control FB, nothing else. Every ms spent there is jitter added to OB1.
        • Hand data between OB1 and interrupt OBs through dedicated DB areas, written on one side only (one owner per direction — the Ch. 18 rule, applied across priorities).
        • For multi-value handovers, use a valid flag written last: fill the fields, then set newDataValid := TRUE; — the reader checks the flag, consumes, clears it.
        • On S7-1500, UMOVE_BLK copies a block uninterruptibly when you truly need atomicity.
        Check yourself

        Why does a PID loop belong in OB30 rather than OB1?

        The integral and derivative terms multiply by the sample time. A varying OB1 cycle makes the effective tuning drift with program load.

        What does merely adding an empty OB82 to a project change?

        For several fault classes the CPU's reaction depends on whether the matching error OB exists. An empty OB says "I am handling this — stay in RUN."

        OB1 writes three Real setpoints that OB30 reads. The safe pattern is…

        The flag-written-last pattern guarantees OB30 never consumes a half-updated set, even if it preempts OB1 between assignments.
        Chapter 16

        Indirect access & VARIANT

        Ninety percent of "generic" programming is runtime array indexing plus Array[*] — you learned both in Chapter 9. This chapter is the last ten percent: blocks that accept any type, and true references. S7-1500 territory, mostly.

        VARIANT: a checked, type-aware handle

        A Variant InOut parameter accepts anything — the block then asks what it got. Unlike the old S7-300 ANY pointer, every access is type-checked at runtime:

        References: REF_TO

        A REF_TO is a typed reference — closer to a pointer, still safe. Where Variant copies, a reference works in place:

        The ^ is the dereference operator; always guard against NULL. References shine in exactly one pattern: select one element of a structure array once, then work on it through many statements without repeating the index arithmetic — clearer and faster.

        Know when to stopThere is also PEEK/POKE for raw byte access to non-optimized areas. It exists for protocol edge cases and migrations — if you reach for it in normal machine logic, the design took a wrong turn several chapters ago. Typed interfaces (UDT, Array[*]) beat clever indirection in every review, every handover, every 2 a.m. call.
        Check yourself

        The main practical difference between Variant and the classic ANY pointer?

        TypeOf, VariantGet/VariantPut and friends validate the type at runtime — wrong-type access fails detectably instead of corrupting memory.

        What does #pMotor^.cmdRun := TRUE; write to?

        That's the point of a reference: ^ reaches through to the original data. No copy-out/copy-back cycle.
        Chapter 17

        Program architecture

        Everything so far was about writing a good block. This chapter is about writing a good program — the layer that decides whether your project is maintainable in year three or a haunted house.

        Three layers, strictly ordered

        LayerBlocksKnows about
        CoordinationOB1, OB30…, one thin "Main" levelWhich areas exist and in what order to call them
        Process / areaFB per machine area: FB_Infeed, FB_SawStation, FB_CIPThe sequence and interlocks of its area; owns its state machines
        DeviceLibrary FBs: motor, valve, analog channel, driveOne physical device class. Nothing about the plant

        Rules that scale

        • Data flows down as parameters, up as status. An area FB calls device FBs through their interfaces; devices never reach up or sideways. Cross-area needs go through the coordination layer.
        • No M-memory (bit memory). Everything lives in DBs with names. M-flags are the untyped global variables of the PLC world — the Siemens guidelines say the same.
        • One global DB per concern: DB_HMI (curated operator interface), DB_Recipe, DB_Comm. Not one giant "DB_Global" that everything writes.
        • Naming as documentation: FB_/FC_/DB_/UDT_ prefixes, devices named by plant code (M301_Conveyor), verbs for commands (cmdStart), states as adjectives (running, fault). Pick the convention on day one; the styleguide in Ch. 22 is a ready-made one.
        • Libraries, not copy-paste. Put released device FBs and UDTs into a TIA project library / global library as versioned types. Fixing a bug then means "update instances," not "find all 14 copies."
        • Version control: export blocks as external sources (or use TIA's workspace/VCI features) and keep them in git. Text SCL diffs — use that superpower; it's half the reason to write SCL at all.
        The testOpen OB1. Can a stranger see what the machine is in ten seconds? Open any device FB. Could you drop it into a different project unchanged? Both yes → the architecture is right. The companion source files follow this layering.
        Check yourself

        A device FB needs to know whether the other conveyor is running. It should…

        Sideways reads couple two devices forever. The area layer knows both devices exist — it wires status of one into an interlock input of the other.

        Why do the guidelines say to avoid M (bit memory) entirely?

        It's an architecture argument, not a performance one: every M-flag is a hidden coupling that cross-reference archaeology has to dig up later.
        Chapter 18

        Pitfalls & debugging

        The greatest hits

        • Setting an output in two places. The last write in the scan wins; the earlier one is invisible dead code. One owner per output, always.
        • Timer starved inside an IF (Ch. 8). Call system FBs unconditionally; gate their inputs.
        • Temp read before write (Ch. 5). Random behavior that simulation may hide.
        • Integer division (Ch. 6). a / b * 100 with integers is almost always a bug.
        • Missing ELSE branches that should reset flags — a warning that latches on forever because only the "set" path was written.
        • Waiting inside a loop. Scan-time overrun → CPU stop. Sequences wait across cycles via state machines, never within a cycle.
        • Comparing Reals with =. After math, #x = 10.0 may never be true. Compare with a tolerance: ABS(#x - 10.0) < 0.001.
        • Unclamped indices from HMI/comms (Ch. 9).
        • Wrong sample time for control loops (Ch. 13).

        Debugging workflow in TIA Portal

        • Monitor mode (glasses icon): live values appear inline next to each SCL line; Bool expressions show green/gray highlighting of which branch is active.
        • Watch tables: group the tags of one problem (step number, transitions, timers) and watch them together; force outputs only with the machine physically safe.
        • Breakpoints exist in PLCSIM — but on a real, running machine you don't halt the CPU. Instead, add trace: the S7-1200/1500 Trace tool records tags at scan resolution — the PLC world's oscilloscope, unbeatable for "it glitches for one cycle" bugs.
        • Cross-reference (Ctrl+Shift+R) answers "who writes this tag?" — the first question in every double-write hunt.
        • Compile early, compile often. The SCL compiler's warnings (implicit conversions, unreachable code) are telling you about future site visits.
        Simulate firstPLCSIM runs your exact compiled code on your laptop. Build a habit: every FB gets exercised in PLCSIM with a watch table (or a small test OB toggling its inputs) before it ever meets hardware. It's the closest thing our field has to unit testing — and with TIA Portal Test Suite (Advanced), actual scripted unit tests exist too.

        Chapter 20

        Exercises

        Do these in order, in PLCSIM. Write the block, wire a small test OB, watch it run. Solutions fold out — but struggle first; the struggle is the course.

        1 · Pump down-time protection Basics · Ch. 6–8

        A pump may only restart 10 s after it stopped (motor cooldown). Write FB_PumpGuard: input cmdRun, output pumpOn. Starting is delayed until the cooldown from the previous stop has elapsed; stopping is immediate.

        Show solution

        The self-holding term #pumpOn OR NOT #tCool.Q is the key: the lockout only blocks starting, never running.

        2 · Tank level with hysteresis and dry-run trip Basics · Ch. 6, 10

        Raw analog 0–27648 = 0–4.0 m. Start the feed pump below 1.2 m, stop above 3.4 m (hysteresis, no chatter). If level reads below 0.05 m while the pump runs for more than 5 s, latch a dry-run fault that only a reset input clears.

        Show solution

        3 · Zone scanner Arrays · Ch. 7, 9

        Given temps : Array[1..24] of Real and one shared limit, produce: a Bool alarm array, the count of zones in alarm, and the index of the hottest zone. One FOR loop total.

        Show solution

        4 · Star-delta starter State machine · Ch. 8, 11

        On start: close main + star contactors; after 6 s open star, wait 100 ms (arc extinction!), close delta. stop or trip opens everything immediately. Star and delta must be mutually exclusive by structure, not by hoping.

        Show solution

        Deriving both contactors from one step variable makes simultaneous closure structurally impossible — the hardware interlock on the panel is then a second, independent layer. And note the #stepOld term: without it the gap step would be skipped entirely, because the shared timer's IN never drops between star and gap (the Ch. 11 shared-step-timer trap). This version runs in the Playground — try it.

        5 · Telegram builder Strings · Ch. 10

        Build the string 'B<batch>;W<weight>;' — e.g. 'B0042;W12.50;' — from batchNo : Int and weight : Real, freshly on each rising edge of send. (Hint: VAL_STRG gives you width and precision control; a simpler version with INT_TO_STRING/REAL_TO_STRING is acceptable.)

        Show solution

        Note the whole build is gated behind the edge — string work happens once per request, not every scan (Ch. 10 warning).

        6 · Recipe lookup UDTs + strings · Ch. 9, 10

        Given recipes : Array[1..20] of "UDT_Recipe" (fields: name : String[16], tempSet : Real, mixTime : Time), write logic that, on a rising edge of load, finds the recipe whose name equals wanted : String[16], copies its setpoints to outputs, and sets notFound if no name matches. Stop searching at the first hit.

        Show solution

        Strings compare directly with = (exact, case-sensitive). The #notFound := TRUE before the loop plus clearing it on a hit avoids a separate "found" flag and an ELSE tangle.

        7 · Capstone: three-station conveyor Integration · everything

        Design freely: infeed conveyor, saw station, outfeed. Photo eyes at each station; the saw takes 4 s; conveyors must never run while the saw is down; an emergency stop resets everything; the HMI shows a step number and per-motor fault codes. Use FB_MotorCtrl from Ch. 12 for all three drives and a sequence FB in the style of Ch. 11. No fold-out solution for this one — when it runs in PLCSIM and you can explain every line, you've finished the course.

        Chapter 21

        Final exam

        Twenty questions across the whole manual. Answer them all; your score appears below and your best run is remembered in this browser. No time limit — but no peeking either. Aim for 18+ before calling yourself fluent.

        0 / 20
        The exam

        1 · Which symbol assigns a value?

        := assigns; = only compares; == doesn't exist in SCL.

        2 · What is 9 / 4?

        Integer operands → integer division, truncated.

        3 · "Output comes on only after the input has been TRUE for 2 s" — which timer?

        On-delay. TOF delays the off; TP makes a fixed pulse.

        4 · A TON is only called inside IF #run THEN. When #run drops mid-timing, the timer…

        Uncalled = not executed. Call unconditionally; gate IN.

        5 · R_TRIG.Q is TRUE for…

        It converts a level into a single-cycle event.

        6 · Which section's variables are garbage at the start of every call?

        Temp is uninitialized scratch — write before read, every call.

        7 · Passing a big ARRAY/STRUCT to an FC goes through InOut because…

        Reference semantics: fast, and the block works on the caller's actual data.

        8 · CASE selects on…

        Integer selector; labels are integer literals, lists, and ranges.

        9 · FOR #i := 0 TO 7 DO runs…

        Both bounds inclusive: 0,1,…,7.

        10 · A WHILE loop that waits for a photo eye to change will…

        Inputs don't refresh mid-scan. Cross-cycle waiting = state machine.

        11 · The robust way to test a computed Real against 10.0:

        Floating-point math rarely lands exactly on a value — compare with a tolerance.

        12 · A PLC data type (UDT) primarily buys you…

        Define the thing once; every motor/valve/channel becomes an instance of it.

        13 · Inside an FB, the bounds of an Array[*] InOut come from…

        Queried at runtime — that's what makes the block size-agnostic.

        14 · msg : String; (no size) reserves…

        Always size strings: String[32] costs 34 bytes instead.

        15 · In a CASE step machine, outputs should be written…

        Derived outputs can never be stale and are never double-written.

        16 · Two consecutive timed steps share one TON via IN := (#step=10) OR (#step=20). Without a stepOld reset term…

        ET only resets when IN drops. The transition keeps IN TRUE — the Ch. 11 trap.

        17 · Closed-loop control belongs in a cyclic interrupt OB because…

        Ti and Td act per-sample; jittery sampling = drifting tuning.

        18 · Integrator anti-windup means…

        Otherwise a long saturated phase stores a mountain of integral that must unwind as overshoot.

        19 · Your Int arrives at a PC as 256× its value. The classic cause:

        Swapped bytes: 16#0001 read as 16#0100. Use SWAP or define the telegram byte-exactly.

        20 · OB100's job in a well-designed program is…

        Deliberate reset or deliberate resume — never "wherever the retained RAM happened to be."
        Chapter 22

        Roadmap & resources

        A realistic mastery path

        • Weeks 1–2 — Syntax fluency. Chapters 1–8, alternating between the Playground (instant feedback on timers and edges) and PLCSIM (the real toolchain). Goal: write timers, edges, and CASE from memory. The quizzes should feel easy on a second pass.
        • Weeks 3–4 — Data modeling. Chapters 9–10. Import the companion source files into a TIA project and rebuild a small ladder project you know entirely in SCL with UDTs.
        • Month 2 — Sequences. Chapter 11 until step machines are reflex — including the shared-step-timer trap. Do exercises 4 and 6.
        • Month 3 — Library thinking & loops. Chapters 12–13; build your personal device library (motor, valve, analog channel, PI wrapper) and reuse it in the next project.
        • Month 4 — Systems. Chapters 14–17: comms, interrupt design, and program architecture. Then the capstone exercise — a complete small machine in PLCSIM, layered as Chapter 17 preaches.
        • Checkpoint — the final exam, cold. 18+ out of 20 and the fundamentals are yours.
        • Ongoing — read other people's code (open-source S7 projects, Siemens application examples), and study the official Programming Styleguide — consistency is what separates a library from a pile of blocks.
